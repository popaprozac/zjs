# Z language findings — upstream handoff

Work items for **z-lang**, generated by the
[ZJS Z rewrite](superpowers/specs/2026-09-14-zjs-z-rewrite-design.md).

Each item is written to be picked up cold: what ZJS needs, a concrete spec,
the exact files in both compilers, known traps, and an acceptance bar. Nothing
here requires reading the ZJS codebase or this conversation.

## Status ladder

Every item carries one of four statuses. The ladder exists so that a
persuasive proposal never becomes an accidentally approved API, and so an
upstream fix is not called done before the consumer exercises it.

| Status | Meaning | Who advances it |
|---|---|---|
| `proposed` | ZJS hit a gap and suggested a shape. **Not a decision.** Any API spelling written here or in a probe is illustrative. | Claude records |
| `approved` | Zach has agreed to the direction; spelling may still change. | Zach |
| `implemented` | Landed in z-lang, with a commit and a stated supported surface. | Codex |
| `consumer-verified` | ZJS exercised it in real code, dropped its workaround, and recorded the commit. **Only this closes the loop.** | Claude |

Items also note whether they **block** progress, since most do not.

Confirmations stamped with a revision are **Stage 0** reproductions unless
stated otherwise; they are not a claim of native-compiler verification.

Two operating rules, per the agreed handoff model:

- **One writer per checkout.** ZJS never writes to z-lang. Probe runs keep
  their build cache inside the ZJS tree, not z-lang's.
- **Pin the compiler.** ZJS builds and probes against a recorded revision
  ([`z/Z_LANG_REVISION`](../z/Z_LANG_REVISION)), not whatever is checked out,
  so results are reproducible and a mid-edit tree cannot produce a misleading
  probe result.

## Ground rules for any change below

These come from z-lang's own README and docs conventions. They apply to every
item and are not repeated per-item.

1. **Two implementations must stay in parity.** Stage-0 (TypeScript, in
   `compiler/src/`) is the parity authority; the fixed-point native frontend
   (Z, in `compiler/frontend/`) must match. A change landing in only one is
   incomplete.
2. **Docs are part of the change.** New language semantics update
   `docs/language-reference.md`; new implementation slices update
   `docs/bootstrap-status.md` and add a runnable example under `examples/`.
   Temporary limitations belong in bootstrap status, never in the language
   contract.
3. **Acceptance is `bun run test`** plus the relevant tier
   (`bun run test:language`, `test:self-hosting`, …), and for anything touching
   codegen, a self-hosting run must still reach a byte-identical fixed point.
4. **Ordering.** Wave 1 items are independent of each other and can go in
   parallel. Wave 2 items want design agreement before implementation.

## G1 — Hex and binary integer literals

**Status:** `consumer-verified`
**Implemented:** z-lang `135b64c9` — radix literals and digit separators
**Verified:** ZJS `b00f7b4` — engine NaN-box constants respelled in hex, the
shift-from-small-value workaround removed. Probe `numeric-literals`.
**Note:** the `isIntegerLiteral` trap below was handled; the shipped example
covers `0x1e5` explicitly. One limitation found on adoption: `0xFFFE << 48`
still fails because the literal types as `i32` in a shift — see G13. Full-width
constants sidestep it, which is what the engine uses.

### Why
Every NaN-box constant, bit mask, opcode, and Unicode range in a JS engine is
written in hex. Today `0xFFF8000000000000` is a parse error, so all of them
must be hand-converted to decimal — at exactly the places where a reviewer's
ability to verify a bit pattern by eye is what prevents bugs. The reference
engine's own source comments this as a hazard it had to work around.

### Spec
Accept `0x`/`0X` hex and `0b`/`0B` binary integer literals wherever a decimal
integer literal is accepted. Value, type inference, and contextual typing are
unchanged — only the spelling is new. Underscore digit separators
(`0xFFFF_0000`) are desirable and cheap to add at the same time; decide
explicitly rather than by omission.

### Where
| Compiler | File | Note |
|---|---|---|
| Stage-0 | `compiler/src/lexer.ts:326` | the `/[0-9]/` scanner with optional `.` and exponent |
| Native | `compiler/frontend/lexer.zs:501` | mirrored scanner, `isDigit` at `:130` |

### Traps — read these before starting
- **`isIntegerLiteral` is `!/[.eE]/.test(value)`** (`compiler/src/sema.ts:21293`).
  `0xE5` and `0x1e5` contain `E`/`e` and would be **misclassified as floats**.
  The same test is duplicated inline at `compiler/src/codegen-c.ts:13264`
  (`/[.eE]/.test(...) ? "f64" : "i32"`). Both need to become prefix-aware.
- Other `/^[0-9]+$/` guards exist — e.g. fixed-array lengths at
  `compiler/src/parser.ts:134` and a capacity check at
  `compiler/src/sema.ts:12027`. Decide per-site whether hex is permitted there.
- Literal value extraction uses `BigInt(spelling)` and `Number(spelling)`
  (`compiler/src/sema.ts:21231`, `:21361`), which already handle `0x`/`0b`
  correctly. Separators do **not** parse and would need stripping first.
- C emission can pass `0x` through unchanged, but **must strip separators** if
  those are accepted.

### Done when
Hex and binary literals parse, infer, range-check, and emit identically to their
decimal equivalents in both compilers; a runnable example covers a `u64` mask
built from hex; `docs/language-reference.md` numeric-literal text is updated.

## G2 — Exact float bit representation

**Status:** `consumer-verified`
**Implemented:** z-lang `dee8ea80` — as methods on the primitives
(`f64.fromBits(u64)` / `.toBits()`, `f32.fromBits(u32)` / `.toBits()`).
**No `std/bits` module was added**; the proposed free-function shape below was
not taken, and the shipped spelling is the better fit for Z.
**Verified:** ZJS `0f5c94e` — the NaN-box encode/decode path is now ordinary Z
and `value.zs` contains no `raw c` at all. Probe `float-bits`.
**Why it mattered beyond a round trip:** NaN *payloads* survive, which is the
property NaN boxing depends on — boxing stores data in payload bits, so
canonicalization would silently destroy values. Signed zeros and infinities
are covered by an engine test.
**Still open:** broader bit operations (popcount, clz, ctz, byteswap, rotates)
and integer reinterpretation (G11) remain separate work.

### Why
`f64`↔`u64` bit-reinterpretation is the foundation of NaN boxing — the single
most load-bearing operation in the engine. Z has no intrinsic, so it needs a
`raw c` helper per direction. Verified working, but every engine that does this
needs it, and it belongs in the language rather than in each consumer's escape
hatches. Zen-c had the identical gap and solved it the identical way.

### Spec
A new standard module exposing, at minimum:

| Function | Lowering |
|---|---|
| `bitcast` f64→u64, u64→f64, f32→u32, u32→f32 | `memcpy` type-pun, or `__builtin_bit_cast` |
| `popcount`, `clz`, `ctz` | `__builtin_popcountll`, `__builtin_clzll`, `__builtin_ctzll` |
| `byteswap` | `__builtin_bswap{16,32,64}` |
| `rotateLeft`, `rotateRight` | idiom clang recognizes |

`bitcast` is value-preserving at the bit level by definition and must **not**
route through Z's checked numeric-conversion path — it is a distinct operation
from `u64(value)`, and the diagnostic for confusing the two should say so.

### Where — the recipe
`std/math` is the template. Adding a standard module function touches exactly
these, confirmed by tracing `math.trunc`:

| Compiler | Files |
|---|---|
| Stage-0 | `compiler/src/standard-library.ts` (registry entry + `standardModuleMemberNames`), `compiler/src/sema.ts` (call checking), `compiler/src/language-service.ts` (hover/completion) |
| Native | `compiler/frontend/semantic-standard-library.zs`, `module-resolver.zs`, `lowering-ir.zs`, `c-emitter.zs` |
| Wiring | `compiler/src/modules.ts` — register the `std/bits` header name |

The registry is pleasantly table-driven — `math.trunc.f64` is four lines
mapping to `__builtin_trunc` (`compiler/src/standard-library.ts:79`).

### Done when
`import { bitcast } from "std/bits"` round-trips an `f64` through `u64` and back
in both compilers, with a runnable example and reference documentation.

## G3 — `std/math` breadth

**Status:** `proposed` · **Size:** medium · **Priority:** high

### Why
`std/math` currently exports **exactly one function: `trunc`**. ECMA-262
requires the full `Math.*` surface, and the engine needs `fmod`, `pow`,
`isnan`, `isfinite`, and infinity constants internally for number formatting
and comparison semantics.

### Spec
Extend `std/math` to the C `math.h` surface that `Math.*` needs: `sqrt`, `cbrt`,
`pow`, `exp`, `expm1`, `log`, `log2`, `log10`, `log1p`, the trig and inverse-trig
family, `sinh`/`cosh`/`tanh` and inverses, `atan2`, `hypot`, `fmod`, `floor`,
`ceil`, `round`, `abs`, `sign`, `min`, `max`, plus `isnan`, `isfinite`, and
`infinity`/`nan` constants. Both `f32` and `f64` where the C builtin has both.

Most map one-to-one onto `__builtin_*`, exactly as `trunc` does — this is
breadth work, not design work.

**One genuine design question:** NaN and infinity are values Z's type system
currently has no way to name, and Z's numeric conversions deliberately trap on
non-finite values. Producing and comparing them needs an explicit, documented
answer rather than an accident of the C lowering.

### Where
Same recipe as G2, minus the new-module registration — `std/math` is already
wired in `compiler/src/modules.ts:642`.

### Done when
The `Math.*` surface is expressible in Z without `raw c`; non-finite value
semantics are documented in `docs/language-reference.md`; a runnable example
exercises the non-finite cases.

## G11 — Checked numeric conversion cannot reinterpret a bit pattern

**Status:** `consumer-verified` — z-lang `7d5e557e` (in pin `4bef7756`), ZJS `8037e98`
**Confirmed:** z-lang `00864194`, Stage 0 reproduction
**Blocks:** no
**Priority:** high — it is the integer half of what `dee8ea80` landed for floats

Shipped as `negative.toBits(): u32` and `i32.fromBits(bits): i32`, the
recommended spelling below. `value.zs` now boxes and unboxes int32 payloads
through them and the manual sign folding is gone. Probe `integer-bits` LANDED.

### Why
`u32(-42)` **traps**. Z's numeric construction is value-preserving by design,
which is right for ordinary code — but NaN boxing needs the opposite: C's
`(uint32_t)i` reinterpretation of the sign bit. There is no way to express that
in Z today, so the engine folds the sign with arithmetic standing in for a
representation change (`int32Value`/`asInt32` in `z/engine/value.zs`).

### Codex's recommendation from review — not an approved extension

```z
const negative: i32 = -42;
const bits: u32 = negative.toBits();
const restored = i32.fromBits(bits);
```

This mirrors the `fromBits`/`toBits` pair shipped for floats. It is a
**recommendation, not an approved API**. In particular `u32.fromBits(negative)`
was considered and is **not approved**. Checked numeric constructors keep their
existing trapping behaviour regardless of what is chosen.

Probe `integer-bits` is written against the recommended
spelling and says so.

### Done when
An `i32` round-trips through `u32` and back preserving its bit pattern, without
`raw c` and without manual sign folding, and the engine's sign-folding code is
deleted.

## G12 — No monotonic clock

**Status:** `proposed` · **Size:** small · **Priority:** medium
**Found:** Phase 0 spike, building the benchmark harness.

`std/time` exposes only `sleep` and `delay`. There is no way to read a clock, so
**any benchmark, profiler, or timing-sensitive code in Z must drop to `raw c`**
for `clock_gettime`. z-lang's own benchmark suite is written in TypeScript, which
is likely why this has not surfaced.

Ask: `monotonicNanoseconds()` and a wall-clock read in `std/time`. Monotonic is
the one that matters; it must be guaranteed non-decreasing and documented as
such.

## G13 — Integer literals are not contextually typed in some positions

**Status:** `consumer-verified` — expectation case z-lang `4bef7756`;
ternary and shift cases z-lang `3f96e759`; ZJS adoption recorded with the
pin advance to `3f96e759`
**Confirmed:** z-lang `00864194`, Stage 0 reproductions
**Blocks:** no. All three probes LANDED; the engine's typed-binding
workarounds for `toEqual` literals and the AST dump's ternary flags are
removed. The NaN-box constants stay spelled full-width by choice.

### Intended principle
Contextual typing of **literals** — never implicit conversion of an
already-typed variable.

### Confirmed gaps, each with its own probe

| Case | Behaviour at `00864194` (all fixed by `3f96e759`) | Probe |
|---|---|---|
| `return flag ? 7 : 6` from a `u64` function | fails: expected u64, found i32 | `literal-in-ternary` |
| `const mask: u64 = 0xFFFE << 48` | fails: the shift is checked as `i32` before destination context reaches the literal | `literal-in-shift` |
| `expect(handle).toEqual(1)` with a `u32` handle | `z check` accepts; generated C fails `-Wsign-compare`. Generated storage is `uint32_t actual` versus `int32_t expected = 1U`: contextual literal emission and the expectation's storage metadata disagree | `literal-in-expectation` (needs `z test`) |

The third case matters beyond ergonomics: a Z type error reaching clang with no
Z source location is a diagnostic escape, whatever happens with contextual
typing.

### Not gaps — removed from this item after review
- `sum >= -2147483648 && sum <= 2147483647` with an `i64` operand **works**.
- A direct `u32` comparison against `1` **works**.

Earlier drafts of this item listed both; the probes were split so one early
failure cannot hide the others.

## G14 — `while (true)` is not recognized as diverging

**Status:** `proposed` · **Size:** small · **Priority:** low
**Found:** Phase 0 spike, writing the dispatch loop.

A `while (true)` whose only exits are `return` still reports *"function must end
with a return value"*, requiring an unreachable trailing return. This is the
exact shape of every bytecode interpreter loop, so it is not an obscure case.

Ask: treat a `while (true)` with no `break` as diverging in flow analysis.

## G15 — A runtime trap reports nothing

**Status:** `proposed` · **Size:** small · **Priority:** medium (DX)
**Found:** Phase 0 spike, debugging G11.

When generated code calls `abort()` — a failed bounds check, a failed checked
conversion, a failed checked shift — `z run` exits **1 with no output at all**.
`z check` says `ok` and `z emit` succeeds, so there is nothing to work from.
Diagnosing G11 meant reading the emitted C to find which `abort()` had fired.

Ask: trap sites should identify themselves — which check, at which Z source
position. These are compiler-generated aborts, so the information is available
at emission time.

## G16 — `inout` through indexed storage

**Status:** `proposed` — scope corrected after review
**Confirmed:** z-lang `00864194`, Stage 0 reproduction
**Blocks:** no. The method-call form is the workaround and the engine uses it.

### Scope, precisely
`allocate(inout slot.heap)` through a plain field projection **already works**.
What fails is specifically the **indexed-storage boundary**:

```z
allocate(inout registry.slots[index].heap);
//        ^ requires inout <mutable binding> for parameter 1
```

Codex classifies this as a **conservative implementation restriction, not a
language rule** that mutating APIs must be methods. An earlier draft of this
item overstated it as "inout arguments must be plain bindings"; that was wrong.

### Why it matters for ZJS
An engine reaches through collections to mutate nested state constantly — a
context's heap, a frame's register file, a shape's transition table. Today each
of those APIs is a method on the receiver, because a method call on the same
projection (`registry.slots[index].heap.allocate(...)`) is accepted. That is a
fine design and the engine keeps it; it is recorded here so the restriction is
known rather than rediscovered.

### Left for upstream review
Broader ownership support through indexed storage. If the restriction is kept,
the diagnostic should name the method workaround, since "requires inout
<mutable binding>" describes the symptom without pointing at the fix.

Probe `inout-indexed-storage` exercises both the working field case and the
failing indexed case.

## G17 — No outward integer conversion for enums

**Status:** `proposed` · **Size:** small · **Priority:** medium
**Confirmed:** z-lang `00864194`, Stage 0 · **Blocks:** no
**Found:** Phase 3, writing the token dump for the lexer oracle.

Neither a plain `enum` nor a `c enum` with a declared representation can be
read as an integer: `u8(kind)` is rejected with *"numeric construction
requires a numeric value"*. A `c enum` already fixes its representation; the
ask is to read that representation outward. Inward (integer → enum)
construction is deliberately **not** requested here — that is G5's territory.

ZJS use: serializing token kinds and cell tags, and any table indexed by an
enum. The engine generates a 110-arm `match` (`kindCode` in
`z/engine/token.zs`) to reproduce the reference numbering instead.
Probe `enum-integer-code` (spelling is a proposal).

## G18 — No byte or character literal

**Status:** `proposed` · **Size:** small · **Priority:** medium (reviewability)
**Confirmed:** z-lang `00864194` · **Blocks:** no
**Found:** Phase 3, writing the lexer.

Z has no `char` type and no way to spell a byte as a character, so a scanner
tests named numeric constants: `z/engine/lexer.zs` opens with ~70 lines of
`const B_SLASH: u8 = 47;` before any logic. A lexer review *is* a review of
those comparisons, and `47` is not reviewable where `'/'` is.

Ask: a reviewable spelling for a `u8` naming an ASCII character. Probe
`byte-literal` proposes `b'/'`; any equivalent is fine.

## G19 — `in` borrow conflicts with a field read of the same value in one call

**Status:** `proposed` · **Size:** small · **Priority:** low
**Confirmed:** z-lang `00864194` · **Blocks:** no
**Found:** Phase 3, keyword lookup.

```z
lookupKeyword(in text, 0, text.byteLength)
// error: overlapping in and value uses of "text" and "text.byteLength"
```

Both uses are reads. The workaround (bind the length first) is harmless but
moves a value away from its use for no safety gain. If the rule is intentional
simplicity, the diagnostic should say so and name the bind-first workaround.
Probe `in-borrow-with-field-read`.

## G20 — Method call on a module-level `const String` mis-lowers

**Status:** `consumer-verified` — fixed in z-lang pin `4bef7756`, ZJS `bf7c95e`
**Confirmed:** z-lang `00864194`, Stage 0 · **Blocks:** no
**Found:** Phase 3, the escape-decoded keyword path. The lexer's keyword
table is a module constant again. Probe `module-const-string-method` LANDED.

```z
const TABLE: String = "abc";
function main(): i32 { return TABLE.byteAt(0) == 97 ? 0 : 1; }
```

`z check` accepts this. The generated C contains `byteAt(0)` with the
receiver dropped, and clang fails: *"call to undeclared function 'byteAt'"*.
The same call on a local `String` binding lowers correctly. This is a
diagnostic escape of the same class as G13c — Z accepts, the backend rejects.
Minimal reproduction: probe `module-const-string-method`
(`BACKEND-REJECTED`). Engine workaround: the table is a function returning
the literal.

Also seen and not filed as findings, for the record: `while` bodies must be
braced (unlike `if`); Z string literals have no `\u` escape; `out` is a
reserved capability word and cannot name a binding.

## G21 — A String's bytes cannot reach native code without a copy

**Status:** `proposed` · **Size:** medium · **Priority:** medium
**Confirmed:** z-lang `00864194`, Stage 0 · **Blocks:** no (worked around)
**Found:** Phase 3, parsing numeric literals.

Decimal literals need C's `strtod` — Z has no string-to-float, and the
reference engine uses `strtod` too. But:

```
function parseDouble(text: String): f64 = raw c { return strtod(text, NULL); }
// error[Z0821]: type "String" cannot cross a raw native boundary in the first tier
```

and there is no way to view a `String` as a `cstring` either. The engine's
workaround copies each byte into a `calloc`'d buffer through a `usize`
handle, calls `strtod` on that, and frees it — exact, but every string-heavy
native call pays an allocation and a loop.

Ask: a non-escaping borrowed view of a String's NUL-terminated bytes usable
as a `raw c` operand or native argument. Probe `string-to-native` proposes
`text.asCString()`; any equivalent that avoids the copy is fine. Separately,
a Z-level `parseFloat` in `std/math` (see G3) would remove this particular
need entirely.

## G22 — `std/memory.replace` on an `Array` field mis-infers its result type in codegen

**Status:** `consumer-verified` — z-lang `476e74b9` (in pin `6d1f72cd`), ZJS `ce3dac0`
**Confirmed:** z-lang `00864194`, Stage 0 · **Blocks:** no
**Found:** Phase 3, swapping the parser's token stream for a template substitution.

Landed as inferred storage from `replace(inout this.field, move
replacement)`. Probe `replace-array-field-inference` `LANDED`; the compiler's
four written-out result annotations are gone.

```z
function swap(inout this, fresh: Array<Item>): usize {
  let previous = replace(inout this.items, move fresh);   // z check: ok
  return previous.length;
}
```

The generated C declares `previous` as `int32_t` and clang rejects the
initialization from the Array struct. **Writing the annotation out —
`let previous: Array<Item> = replace(...)` — compiles and runs**, so the
inferred type is wrong only in the emitter. Same diagnostic-escape class as
G13c and G20: Z accepts, the backend rejects.

Minimal reproduction: probe `replace-array-field-inference`. The parser
appends a substitution's tokens and parses within a window rather than
swapping the array, which stays as its design.

## G23 — `Array` cannot remove its last element

**Status:** `consumer-verified` — z-lang `ac391e43` (in pin `6d1f72cd`), ZJS `ce3dac0`
**Confirmed:** z-lang `4bef7756` · **Blocks:** no
**Found:** Phase 4, the interpreter's register and frame stacks.

Landed as `pop(): Option<T>`, transferring the last element and retaining
capacity. Probe `array-pop` `LANDED`. The runtime's temp-root stack and the
compiler's loop stack push and pop now. The register and frame stacks keep
their live-extent counters on purpose: a frame is a window over the
register stack and the two move together, as in the reference. The
compiler's region stack keeps its counter too, since compiling a `finally`
inline lowers the live extent temporarily and restores it, which a pop
cannot express.

`Array` offers `push`, `clear`, `length`, `isEmpty`, and `freeze`. There is
no `pop`, `remove`, `truncate`, or `resize` — no way to shrink by one. A stack
— the most common growable-array use in an engine — keeps its own
live-extent counter over a monotonically grown array instead; the engine
does this in three places already (registers, frames, loop bookkeeping).
Probe `array-pop` proposes `pop(): Option<T>`; a `truncate(length)` alongside
would serve the stack case directly.

## G24 — A field read of `this` inside a call that borrows `this` mutably is rejected

**Status:** `proposed` · **Size:** small · **Priority:** low
**Confirmed:** z-lang `4bef7756` · **Blocks:** no (worked around)
**Found:** Phase 4, every register write in the interpreter.

`this.setReg(a, this.regs[b])` fails with *"overlapping inout and value uses
of this in one call"*, so each operand is bound to a local first — 17 sites
in the interpreter loop alone. A *method call* on `this` in the same position
(`this.setReg(a, this.reg(b))`) is accepted, so the rule is specifically
about a field projection. The receiver-side twin of G19; both forms are
reads, and argument evaluation precedes the call. If intentional, the
diagnostic should name the bind-first workaround. Probe
`inout-receiver-operand`.

## G25 — A `Mutex` lock callback cannot take ownership of an outer value

**Status:** `proposed` · **Size:** small · **Priority:** low
**Confirmed:** z-lang `4bef7756` · **Blocks:** no (worked around)
**Found:** Phase 4, the eval entry point.

The C ABI receives an owned `String`; the context registry lives behind a
`Mutex`; the `withLock` callback captures the String as a borrow and so
cannot pass it on by move. The engine copies the source per call. The
reference mentions placed `using (move owner)` capture contracts — if that
applies to lock callbacks, the ask is documentation and an example, not a
feature. Probe `lock-callback-ownership`.

## G26 — A String cannot be built from bytes the program holds

**Status:** `consumer-verified` — z-lang `6d1f72cd` (in pin `6d1f72cd`), ZJS `ce3dac0`
**Confirmed:** z-lang `3f96e759` · **Blocks:** no
**Found:** Phase 5, error messages in the interpreter.

Landed as strict `String.fromBytes(bytes)`: borrows through the Slice
conversion, returns owned text, throws `Utf8Error` (from `std/text`, with
`byteOffset` at the end of the valid prefix) on malformed input. Probe
`string-from-bytes` `LANDED`, including the error offset. The engine decodes
through it and keeps its native buffer only as the fallback for malformed
bytes, since JavaScript strings are bytes and a diagnostic must still be
printable; a lossy or consuming variant is not asked for.

JavaScript strings are `Array<u8>` in the engine (byte length, byte
indexing, embedded NULs). Assembling `Cannot read properties of undefined
(reading 'name')` from those pieces is easy as bytes; turning the result
into a `String` is impossible. `String.from` takes a borrowed `cstring` from
native code and nothing accepts an `Array<u8>`, so engine text can never
reach a template literal, `console`, or any String-typed API. The engine
assembles messages as byte arrays throughout instead.

Probe `string-from-bytes` proposes `String.fromBytes(bytes)`; an owned
String from a byte array, with either a caller-guaranteed or a checked UTF-8
contract, is the ask. The inverse direction (G21) and this one together
would let the engine move text across the boundary in both directions
without a native detour.

## G27 — A parameter named `self` collides with the lowered receiver

**Status:** `implemented` — z-lang `93611fe5` (pin `93611fe5`); probe `self-parameter-name` `LANDED`. Not consumer-verified: the engine's one such parameter was renamed to `callee`, which is the better name, and no engine site wants `self`. The probe is the evidence; a real use will close it.
**Size:** small · **Priority:** medium
**Confirmed:** z-lang `3f96e759` · **Blocks:** no (renamed)
**Found:** Phase 7, the builtins' host-function type.

A method's `this` lowers to a C parameter named `self`. A Z parameter of
the same name in that method is accepted by `z check` and rejected by
clang: *redefinition of parameter 'self'*, with no Z source location. A
diagnostic escape of the class G13c / G20 / G22 belong to. Either `self`
should be a reported reserved name, or generated names should be mangled
apart from user names. Probe `self-parameter-name` (`BACKEND-REJECTED`).

## G28 — No truncating conversion from `f64` to an integer

**Status:** `consumer-verified` — z-lang `6d1f72cd` (`math.trunc` in `std/math`), ZJS `ca3272b`
**Confirmed:** z-lang `3f96e759` · **Blocks:** no
**Found:** Phase 7, the builtins' index and length arguments.

`math.trunc` rounds toward zero while keeping the floating type and
composes with the checked conversion. Probe `truncating-conversion`
`LANDED`; the engine's `truncateDouble` calls it and the `raw c`
`__builtin_trunc` is gone. Still open from the same finding: a checked
conversion that names the offending value when it traps (G15), and a
wrapping ToInt32-style narrowing, which stays in `raw c` for now.

`i32(value)` and `u32(value)` on an `f64` are checked and trap on a
fractional value -- and on NaN -- with no diagnostic (G15), so
`parseFloat("-.5")`, `array[1.5]`, and `new Array(2.5)` each took the engine
down before the guard was found. JavaScript narrows by truncation
everywhere (ToInt32, ToLength, ToIntegerOrInfinity), so every such site now
calls a `raw c` `__builtin_trunc` first and compares. The value-preserving
default is right; the ask is a spelled-out truncating conversion
(`value.truncate()`, or `trunc` in `std/math` alongside G3) so the intent is
in Z and not in C. A checked conversion that named the offending value
when it traps would have found these in seconds; that half is G15.

## G29 — A shift that loses bits traps, and there is no wrapping shift

**Status:** `consumer-verified` — z-lang `ff4c68c2` (in pin `0d8cd8c4`), ZJS `4f97215`
**Confirmed:** z-lang `3f96e759` · **Blocks:** no (worked around)
**Found:** Phase 7, Math.random -- and, on inspection, the interpreter's `<<`.

Landed as `wrappingShiftLeft(count)` on the receiver's exact type, with a
checked bit count. Probe `wrapping-shift` `LANDED`. JavaScript's `<<` and
the xorshift step of `Math.random` are in Z; both `raw c` shift helpers
are gone.

`state << 25` on a `u64` traps when the high bits leave the word, silently
(G15). JavaScript's `<<` discards those bits by definition, so the
interpreter's shift handler was one `3 << 31` away from the same trap, and
a xorshift generator cannot be written at all. The arithmetic operators
have `wrappingAdd` / `wrappingSubtract` / `wrappingMultiply`; the shifts
have no wrapping form. Both sites now go through `raw c`. Ask:
`wrappingShiftLeft(count)` beside the other wrapping operations. Probe
`wrapping-shift`.

These need agreement on direction before implementation. Each has a real

## G4 / G5 — Interpreter dispatch: no `goto`, and `match` is enum-only

**Status:** `proposed` · **Size:** large · **Priority:** decide after the ZJS spike

### Why
A bytecode interpreter's dispatch loop is the hottest code in the program. The
established designs are computed goto (`goto *opcodeTable[op]`, Hermes/QuickJS)
or tail-called per-opcode handlers. **Z can express neither.** There is no
`goto`, no labels, and `match` accepts only enum variants — no integer subject,
and no integer→enum construction for Z-declared enums, so a `u8` read from a
bytecode stream cannot be turned back into a matchable enum.

**This is not currently blocking.** The reference engine reaches ~2.05×
QuickJS-ng jitless *without* computed goto, and its own source records that the
real lever was value representation, not the dispatch primitive. So this caps
the ceiling rather than gating the project.

### The three candidate answers

**(a) Whole-function `raw c`.** Available today, no language change. The
hottest and largest component of the engine stays C — which is precisely the
outcome a Z rewrite exists to avoid.

**(b) A `dispatch` construct.** Something like `dispatch (opcode) { ... }`
lowering to computed goto with a `switch` fallback. Most direct, and the
largest language addition.

**(c) A checked tail-call effect.** Each opcode handler becomes an ordinary Z
function ending in a guaranteed tail call. **This is the most interesting option
and it is specific to Z.** The reference engine's design study evaluated exactly
this shape and rejected it for Zen-c, because a transpiler "might add cleanup
shims for moved values" that silently break tail-call eligibility — turning a
jump into a call, with worse register pressure than the alternative.

Z does not have that problem. **Z statically knows what cleanup is pending at
every program point.** It can *verify* a tail call is cleanup-free and reject it
with a diagnostic otherwise, where Zen-c could only hope. That converts a
fragile C-level bet into a checked language guarantee — and the feature is
considerably smaller than computed goto.

A narrower version of G5 (integer subjects in `match`, and checked
integer→enum construction) is independently useful and much cheaper than any of
the three.

### Spike verdict — measured 2026-09-14

The Phase-0 spike built and measured all of this. Full data in
[`z/spike/RESULTS.md`](../z/spike/RESULTS.md).

- **Option (a) is dead.** A whole-function `raw c` computed-goto loop ran at
  **0.99×** the C baseline while an `if`-chain written in **ordinary Z ran at
  0.84×** — dropping to C for the dispatch loop was *slower*, and cost Z's
  ownership, type checking, and tooling over the hottest component for nothing.
- **Clang recovers table dispatch on its own.** A dense `if`-chain over 70
  opcodes is promoted to a jump table (verified in the assembly: 1 indirect
  branch plus jump-table data, versus 0 indirect branches and 37 compares at 10
  opcodes). **G4 computed goto is therefore not urgent.**
- **But ISA size costs ~25%** — 0.84× at 10 opcodes versus 1.05× at 70. A real
  engine has ~200, and the trend is the wrong way.
- **Option (c) has an empirical case.** Function-value table dispatch works in Z
  today with no language change, but is the slowest variant at **1.25×**,
  because without a tail call each handler returns to the loop and pays a halt
  check per dispatch. Removing exactly that return-and-recheck is what a checked
  tail-call effect buys.

### Recommendation — changed by the evidence

**Promote the narrow half of G5 — integer subjects in `match`, lowering to a
dense switch — to Wave 1.** It is cheap, it is the direct intervention against
the ~25% ISA-size cost, and it is now evidence-backed rather than speculative.

**Leave G4 and the tail-call effect in Wave 2**, and gate them on one more
measurement: the same comparison at ~200 opcodes and on x86-64. If the if-chain
still lands near 1.05× there, neither is needed.

## G9 — No raw pointer types

**Status:** `proposed` · **Size:** large · **Priority:** decide after the ZJS spike

### Why
Z's unsafe pointers are scope-local: not storable in a field, not
dereferenceable, not returnable, not capturable. The reference engine writes
typed pointers throughout (`ZjsValue*`, `f.code_len`). Z's available paths are
pointer-as-`usize` with `raw c` accessors — verified working, but with no
Z-level type safety over the object graph and roughly two thousand such sites —
or an object graph that avoids pointers entirely.

### The ZJS-side answer may reduce what Z needs
The rewrite is seriously considering **handle-based cells**: cells live in
Z-owned pools and a "pointer" becomes a 32-bit handle rather than an address.
If that wins in the spike, ZJS needs *no* new pointer capability from Z at all,
and this item downgrades sharply. The spike settles it.

### Spike verdict — measured 2026-09-14
Handle-based cells cost **~5%** versus the raw-pointer heap (0.88–0.90× against
0.84–0.86×), and the rewrite is adopting them on that basis. **G9 therefore
largely dissolves**: with handles, no raw pointer touches the JS object graph at
all, and Z gets position-independent cells that make the mmap-ready AOT bundle
nearly free. Re-confirm at engine scale, where a real object graph's cache
behavior may differ from a 4-field toy.

### If pointers are needed anyway
The ask is a storable, typed, explicitly-unsafe pointer with declared
provenance — not a general escape from the ownership model. Scope it against
the existing `unsafe` tier's deliberate narrowness, which is a design position
worth preserving.

## G8 — No thread-local module state

**Status:** `proposed` · **Size:** medium · **Priority:** medium

### Why
`Once<T>` publishes one application-lifetime root, not one per thread. The
reference engine uses `_Thread_local` globals with one context per thread, and
Zapp's multi-worker model depends on that shape.

### Sharpened by Phase 1 — this is worse than it first looked

Building the Phase 1 scaffold hit a hard corner that the doc survey missed:

1. `Once<T>` accepts only a class whose lifecycle is **main-bound**.
2. Marking the class `on thread.main` makes every field main-affine.
3. `export c function` **rejects executor-affine functions**.

So the obvious composition -- publish engine state through the manifest runtime
root, expose it over the C ABI -- **does not compile**. The way through is a
*vestigial main-bound field* on an otherwise ordinary class, which satisfies
Once while leaving a `Mutex` field thread-shareable. It works, and the
`z-runtime-export` example uses the same trick, but a class needing a field it
never reads in order to be publishable is a design smell.

Concretely, ZJS needs a root that is publishable **without** main-binding,
because a JS context belongs to a worker thread and never touches the main
thread at all.

### Note before building anything
Explicit `inout Context` threading verified clean in Z probes, with no
loan-checker friction, and is arguably the better architecture — it removes the
global rather than reproducing it. **ZJS is likely to take that path
regardless**, which means this may be a "nice to have" rather than a
requirement. Confirm against real Zapp worker needs before spending language
budget here.

## G6 — Array indexing always bounds-checks

**Status:** `proposed` · **Size:** medium · **Priority:** measure first

### Why
`z_bounds_index` is `if (index >= length) abort();`
(`compiler/src/codegen-c.ts:487`), applied to every index with no unchecked
form. In an interpreter that is a compare and branch on every register-file and
bytecode access, in the hottest loop in the program.

### Spike verdict — measured 2026-09-14
Not isolated directly, but the handle/pool variant pays a bounds check on every
cell access and still lands at **0.88× the C baseline**. There is no evidence of
a bounds-check crisis. **Not urgent.**

### Note
**Do not act on this before it is measured.** The branch is perfectly
predicted in practice and may cost near nothing; asking Z to weaken a safety
guarantee on a hunch would be a bad trade. If it does show up, the narrow ask
is an opt-in unchecked-index form with a proof obligation, not globally
disabling the check. The ZJS spike will produce the number.

# Wave 3 — strategic, tracked

## G7 — `export c function` rejects pointer parameters

**Status:** `proposed` · **Size:** medium · **Priority:** low (unblocked)

The C export tier covers integers, floats, `boolean`, `void`, `String` inputs,
`c struct`, and `c enum` — but not pointers. `zjs.h` is `ZjsContext*`
throughout.

**Not blocking:** bridged by a thin generated C shim over `uintptr_t` exports,
which is the same pattern Zapp already uses in
`native/z/framework/worker/zjs/`. The docs note that mapping `in`/`inout`/`out`
onto a public pointer ABI is a deliberate follow-up design decision rather than
an oversight — worth doing properly rather than fast. An opaque-handle export
form (`ZjsContext*` as a named opaque pointer type in the generated header)
would remove the shim without opening the general pointer-ABI question.

## G30 — A C export cannot receive bytes without validating them as text

**Status:** `consumer-verified` — z-lang `0d8cd8c4` (in pin `0d8cd8c4`), ZJS `4f97215`
**Confirmed:** z-lang `6d1f72cd` · **Blocks:** no (worked around)
**Found:** Phase 7, the engine's C API taking JavaScript source.

Landed as borrowed read-only `Slice<u8>` inputs on C exports, expanding to
a pointer and a length at the boundary with no copy or decoding. The
engine's `zjs_z_eval` takes its source that way; the raw C byte reader
and the address-as-integer parameter are gone. Still open from the same
entry: `cstring` as an export parameter, not needed now.

The C-export tier accepts scalars, owned `String`, and checked C-layout
values. A `cstring` parameter is rejected (`Z0830`), and a `String`
parameter is marshalled through the validating conversion, which aborts the
process on malformed UTF-8. JavaScript source and string values are bytes,
so an engine entry point typed `String` turns a script that is not UTF-8
into a host crash. The engine's `zjs_z_eval` now takes the source pointer
as a `usize` and copies bytes through a `raw c` reader, with the shim
casting the pointer; that keeps the host safe but puts the boundary contract
in C rather than in Z.

The ask: a borrowed byte input at the C boundary -- `cstring` accepted as
an export parameter, or a pointer-plus-length `Slice<u8>` view -- so a Z
library can accept bytes from C without asserting they are text. Related:
G21 (bytes out to native) and G26 (bytes to String, now landed).

## G31 — Checked indexing and arithmetic cost the interpreter loop about a tenth

**Status:** `proposed` · **Size:** medium · **Priority:** high
**Confirmed:** z-lang `93611fe5`, measured · **Blocks:** no
**Found:** the performance spike after classes.

Every array index lowers to `z_bounds_index` (compare and abort) and every
`+` on an index to `__builtin_add_overflow` (compare and abort). The
interpreter's inner loop does two to four of each per bytecode
instruction: the instruction fetch, the register reads and write, the
constant table. Measured by rebuilding the generated C with both helpers
made unchecked (no other change): integer loop 0.92 to 0.90 s, calls
0.19 to 0.17 s, constructing 0.56 to 0.52 s, array methods 0.34 to 0.29 s
-- 7 to 13 percent. Combined with switch dispatch (now landed as `match`)
the loop went 0.92 to 0.63 s. `wrappingAdd` already removes the overflow
half where the program can prove the sum fits; the bounds half has no
spelling.

Bounds-only follow-up, as asked: the current generated C (register and
instruction-pointer arithmetic already wrapping, nine checked adds left in
the file) rebuilt with only `z_bounds_index` made unchecked, identical
flags (`-O2`), five runs each, min / median / max in seconds:

| benchmark | checked | bounds unchecked | median gain |
|---|---|---|---|
| integer loop | 0.615 / 0.618 / 0.867 | 0.577 / 0.579 / 0.908 | 6% |
| calls | 0.120 / 0.121 / 0.125 | 0.118 / 0.119 / 0.121 | 2% |
| constructing | 0.201 / 0.203 / 0.204 | 0.183 / 0.184 / 0.185 | 9% |
| array methods | 0.253 / 0.258 / 0.262 | 0.233 / 0.238 / 0.243 | 8% |

Run-to-run spread is under 2 percent except the loop's one slow outlier
each. So the bounds checks alone are worth 2 to 9 percent on these paths;
the earlier 7 to 13 included the overflow checks since removed by
`wrappingAdd`.

The ask: an indexing form that skips the bounds check where the program
asserts the invariant -- `array.at_unchecked(i)`, an `unsafe` index
expression, or a release-mode elision behind a per-function attribute --
with the check kept in debug builds. The register file (`regStack[base +
index]`, base and window both validated at frame push) and the code
segment fetch are the two sites that want it. Probe `unchecked-index`
(`COMPILER-REJECTED`: `Array has no method "atUnchecked"`).

## G32 — A borrowed view of an array field cannot be held across a loop that mutates the owner

**Status:** `proposed` · **Size:** medium · **Priority:** medium
**Confirmed:** z-lang `93611fe5` · **Blocks:** no (worked around)
**Found:** the performance spike after classes.

The interpreter fetches `this.functions[fi].code[ip]` every instruction:
two array indexings, a struct stride multiply, and the checks of G31,
re-derived each time because the loop body mutates `this` and nothing
lets it keep a borrowed view of one field while doing so. In C this is a
local pointer taken once per frame. The engine now keeps all functions'
instructions in one runtime array (`codeSegment`) and fetches
`codeSegment[codeStart + ip]`, which drops one level; the borrow itself is
still not expressible.

The ask: a way to hold an `in` view of a field (or an element) of `this`
for the extent of a loop that only mutates *other* fields -- a
field-disjointness borrow -- so an interpreter's code pointer, register
window, and constant table can each be a local view. The spelling exists:
`view this.code`. Probe `field-view-borrow` (`COMPILER-REJECTED`, Z0205:
cannot mutate `this` while the view is live); the upstream review confirms
sibling-field tracking is conservative at indexed access, and that the
native checker currently permits an element view held across a loop that
pushes to the same array (a separate soundness fix that comes first). The
engine uses neither pattern.

## G10 — Z is macOS-only

**Status:** `proposed` · **Size:** large · **Priority:** strategic

Cross-platform is one of ZJS's six stated goals, and Windows and Linux engine
ports already exist in the Zen-c implementation — they will have nowhere to
land. Z's header-first interop model should make the port tractable, and ZJS
plus Zapp together are a good forcing function for what "cross-platform Z"
actually has to mean. Tracked here as a dependency, not as an ask this project
can scope.

# Verified working — recorded so it is not re-litigated

All confirmed by writing and running Z against z-lang at `99037e8` on
2026-09-14, not read off a status table.

- `u64` bitwise `&`, `|`, `^`, `~`, `<<`, `>>`; wrapping and saturating integer ops.
- `malloc`'d cells addressed as `usize` with indexed load/store through `raw c`;
  lowers to plain `static` C functions that clang inlines at `-O2`.
- `inout Context` threaded through helpers with `in Context` reads alongside —
  no loan-checker friction.
- Copying a cleanup-free value struct out of an `Array<T>`, then mutating the owner.
- `raw c` diagnostics are source-mapped back to the `.zs` line — a missing
  `string.h` import was reported at the correct Z position. Better than expected
  for an escape hatch.
- Emitted C is direct and readable: no boxing, no wrapper allocation.
- **Arrays of function values work**: `Array<(inout Frame, a: usize) => void>`
  can be built, indexed by opcode, and called. Table dispatch is expressible in
  Z today with no language change (it is simply not the fastest option — see
  G4/G5).

### Scale and throughput

- Z's self-hosted frontend: ~115k LOC across 59 modules, including one 34.5k-line
  module, reaching a byte-identical fixed point.
- Checking that graph: **2.3 s** native `z`, 6.9 s through Stage-0/Bun.
- Codegen within ~1% of C on arithmetic, direct C calls, dynamic arrays, and
  struct ownership; stripped binary size equal to C
  (`z-lang/benchmarks/results/checkpoint-2026-09-08-macos-arm64.md`).
